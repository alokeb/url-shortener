# Project Context

## Environment
- Host OS: Debian (desktop)
- Editor: VS Code (native install, not Flatpak)
- Docker is installed directly on the Debian host (rootless, confirmed working) — all builds/tests/runs go through it
- Debian host also has JDK 21 installed, but only for VS Code's Java language server (IntelliSense) — not used for actual builds
- No local Maven install on the host — builds happen via `docker build`, which runs the full Maven build inside the image each time
- Docker Compose (the `docker compose` plugin, v5.3.1) is available on the host for running the app alongside its backing services (PostgreSQL, Redis) locally
- All code lives permanently on the Debian filesystem under ~/mycode
- K8s tooling installed for the Kubernetes phase: `kubectl` (v1.32.3, via Debian's own apt repo — no need for Kubernetes' external apt repo/GPG key) and `minikube` (v1.38.1, via the official `.deb` download since Debian doesn't package it), running a single-node cluster with `minikube start --driver=docker` on top of the existing rootless Docker install. VS Code also has `ms-kubernetes-tools.vscode-kubernetes-tools` and `redhat.vscode-yaml` installed for cluster browsing and manifest schema validation.
- `metrics-server` addon enabled on the minikube cluster (`minikube addons enable metrics-server`) ahead of writing manifests, since it's what the HorizontalPodAutoscaler will read CPU/memory from later — confirmed working via `kubectl top nodes`.
- `helm` (v4.2.3) installed via official binary download (Debian doesn't package it) for `kube-prometheus-stack` — Prometheus + Grafana + Alertmanager + node-exporter + kube-state-metrics, all deployed into the cluster's `monitoring` namespace via `helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace`. Grafana reached via `kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80` (session-only; revisit exposing it through the Ingress once that exists). Admin password: `kubectl get secret --namespace monitoring -l app.kubernetes.io/component=admin-secret -o jsonpath="{.items[0].data.admin-password}" | base64 --decode`.
- App instrumented for Prometheus scraping: `spring-boot-starter-actuator` + `micrometer-registry-prometheus` added to `pom.xml`, `/actuator/prometheus` exposed via `management.endpoints.web.exposure.include=health,prometheus` in `application.properties`. No auth on the endpoint — fine for cluster-internal scraping, worth revisiting if it's ever exposed publicly.
- App fully deployed to the cluster via manifests in `k8s/` (namespace, Secret replacing `.env`, Postgres Deployment+PVC+Service, Redis Deployment+Service, app Deployment+Service+HPA+ServiceMonitor, plus a load-test Job for generating traffic). The app image is built locally (`docker compose up --build`) then copied in with `minikube image load url-shortener-app:latest` — minikube's Docker driver runs its own separate daemon, it does **not** see the host's images automatically. `imagePullPolicy: Never` on the app container reflects that there's no registry to pull from. App Deployment has a `wait-for-postgres` initContainer (plain K8s has no `depends_on`-equivalent at all between Deployments — without it the app crash-loops on a fresh rollout if Postgres's Pod is still starting).
- Grafana set to anonymous/admin auto-login (`grafana.auth.disable_login_form` + `grafana.auth.anonymous` in a Helm values override, applied via `helm upgrade --reuse-values -f ...`) — convenient for solo local dev, but makes Grafana fully open to anything reaching port 3000. Fine while only reached via `kubectl port-forward`; must be revisited before any less-local exposure (NodePort/Ingress).
- **minikube's memory allocation was bumped from its ~7.7GB default to 20GB** (`minikube config set memory 20000`) to support real host-level stress testing — the default cap left almost no headroom once the monitoring stack was running. Note: this config change only takes effect via `minikube delete` + `minikube start`, not a plain stop/start — applying it wiped the cluster (all `k8s/` manifests and the Helm monitoring install had to be reapplied; a Postgres PVC's data does NOT survive a `minikube delete`, only a stop/start).
- Learned from an actual host stress test: this app's memory footprint is mostly fixed per-Pod JVM overhead (~300-400Mi at rest, not much driven by request volume) — pushing real host memory usage up means scaling replica *count* high (see HPA's `maxReplicas: 30`), not raising per-Pod usage. Also, a curl-subprocess-per-request load generator becomes the dominant source of host CPU load itself at high concurrency (forking overhead) well before the app under test does — if a cleaner load test is needed later, a proper load tool (e.g. `hey`) issuing many requests from one persistent process would attribute load more accurately to the app.
- `terraform` (v1.15.8) installed via official binary download (same pattern as minikube/helm - Debian doesn't package it). Full config in `terraform/` deploys everything in `k8s/` plus the monitoring Helm release, to either local minikube or an AWS EC2+k3s instance (`deployment_target` variable) - see `terraform/versions.tf` and `terraform/aws.tf` for the detailed reasoning. Sized to generic minimum system requirements (~1 vCPU/1GB RAM without monitoring, ~2 vCPU/3GB with) rather than pinned to any specific instance type - `aws_instance_type` defaults to `t3.micro`, which happens to meet that minimum and be AWS's free-tier-eligible size, but any instance/VM meeting the requirement works. Both `terraform apply` and `terraform destroy` fully tested end-to-end against local minikube (the AWS path is written but **not** live-tested - no AWS credentials available in this environment to verify it).
- **Terraform requires a two-phase `apply` the first time**: provider blocks (`kubernetes`/`helm`/`kubectl`) get configured before Terraform resolves any resource dependency graph, so they can't wait for a not-yet-existing cluster the way resources can wait on each other - confirmed by testing (a plain `terraform apply` against a stopped minikube fails outright with "context minikube does not exist"). Fix: `terraform apply -target=null_resource.minikube_cluster` (or `-target=null_resource.aws_kubeconfig` for the AWS path) first, then a normal `terraform apply`. Only needed while the cluster doesn't exist yet - subsequent applies are a single normal command.
- The AWS provider has the same eager-configuration problem even with zero AWS resources actually being created (`deployment_target = "local"`) - it tries a real credential lookup (including a slow EC2 IMDS timeout) just to configure itself. Fixed with `skip_credentials_validation`/`skip_requesting_account_id`/`skip_region_validation`/`skip_metadata_api_check` on the provider block, plus feeding it an obviously-fake non-empty placeholder credential when none is set (an empty string is treated as "a present but broken credential" and still falls through to the slow IMDS chain - confirmed by testing; only a non-empty dummy value actually avoids that).
- `null_resource` destroy doesn't automatically undo whatever its `local-exec` provisioner did - confirmed by testing: `terraform destroy` left minikube itself still running (docker container up) until a `provisioner "local-exec" { when = destroy; command = "minikube stop" }` was added to `null_resource.minikube_cluster` explicitly.
- Terraform's default app memory sizing (`app_memory_limit`, shrunk to fit the ~1GB "without monitoring" minimum system requirement) was initially set to 256Mi - confirmed by testing this is actually broken: the app's real resting JVM footprint (~300-400Mi, established earlier this session) exceeds that, causing GC pressure severe enough that liveness-probe HTTP responses started timing out, which made kubelet kill and restart the container in a loop. Fixed by raising the default to 450Mi. That ~1GB minimum is still genuinely tight with Postgres+Redis+app all running (expected, not a bug). `enable_monitoring` defaults to `true` regardless of target (Terraform variable defaults can't reference another variable, so it can't auto-switch based on `deployment_target`) - must be set to `false` by hand in `terraform.tfvars` on a machine only sized to the smaller minimum, since kube-prometheus-stack alone needs 2GB+.

## Project goal
Building a Spring Boot URL shortener, to be:
1. Developed and built/tested via Docker directly on the Debian host
2. Backed by PostgreSQL for persistent storage — shortened URLs need to survive restarts and act as permalinks, and once there are multiple app replicas (see Kubernetes goal below) they all need one shared source of truth, which an in-memory/embedded database can't provide
3. Fronted by a Redis cache for hot short-code lookups, so repeated redirects don't have to hit Postgres every time — like Postgres, Redis is external and shared across all app replicas, unlike an in-process cache which would go stale/inconsistent between pods
4. Re-shortening a URL that's already been shortened should reuse and return its existing short code (a true permalink) rather than minting a duplicate
5. Eventually run as multiple Docker containers in an auto-scalable Kubernetes cluster

## Working agreement

This is a known, accepted tradeoff: slower iteration in exchange for one less environment to fight with. Revisit if the slowness becomes a real blocker.

## Known gotchas
- After restoring the Debian host from a Timeshift snapshot (e.g. to test a clean-machine setup), `docker compose up` can fail with `failed to extract layer ... content digest ... not found` — Docker's local image cache/content-store left inconsistent by the restore, not a project config issue. Fix: `docker compose down`, `sudo systemctl restart docker`, `docker system prune -a --volumes`, then `docker compose up --pull always` to force a clean re-pull. Confirmed this clears it and all three services (app/postgres/redis) come up with no other manual intervention needed.
